## 2. Подготовка без платных запросов

### 2.1 Подготовительный PR «VL-004B-prep» (код; после утверждения этого плана)
Небольшие изменения, каждое с тестами на записанном HTTP:
1. **Ограничитель Search API: не чаще 1 запроса в секунду** (настраивается). Повтор после 429 по-прежнему ограничен.
2. **`--probe`** (ступень 1). Два поиска (RU и COM) и два крошечных вызова моделей (по одному на модель, `max_tokens` ≤ 50). Сырые ответы сохраняются в `research/recordings/phase-b/` с вырезанными секретами; ничего не публикуется в рейтинг. По ним сверяется разбор XML и `json_schema`.
3. **`--seeds <file>` и `--no-discovery`.** Испытание идёт на заданных кандидатах из контрольного корпуса, а не на случайно открытых. Discovery выключен полностью: сейчас даже при `VL_LIVE_MAX_NEW=0` выполняются 3 поисковых запроса discovery.
4. **`research:worker:export --live --as-of D`.** Выгрузка CSV для ручной оценки: конкуренты (статус рынка, вид, URL, цитаты работ) и принятые утверждения (цитата, источник, тип источника).
5. **Сохранение сырых ответов поиска** при `--execute` (с редактированием секретов) для последующего пополнения записанного корпуса.

## 3. Бюджет и оповещения в Yandex Cloud Billing (заранее)
Делает основатель (нужна роль редактора платёжного аккаунта); см. [документацию по бюджетам](https://yandex.cloud/ru/docs/billing/operations/budgets).
1. Консоль → **Billing** → платёжный аккаунт → **Бюджеты** → **Создать бюджет**.
2. Тип: **«К оплате»** (учитывает скидки и промокоды). Сумма: **500 ₽**. Период: текущий месяц.
3. Область: облако и каталог `venture-lab-trial`; сервисы — Search API и AI Studio.
4. Пороги: **10 % (50 ₽), 50 %, 80 %, 100 %**. Получатели — основатель и второй контакт, отдельно для 80 % и 100 %.
5. Второй бюджет — «Остаток средств» с порогом, если аккаунт на предоплате.
6. **Важно.** Бюджет только **оповещает** и не останавливает расход. Автоматическое отключение возможно через триггер с Cloud Functions, но это новый облачный ресурс; в плане он **не используется**. Мгновенная остановка — удаление API-ключа (раздел 5.3).
7. Биллинг в Yandex отражается с задержкой (часы). Поэтому во время прогона оперативный контроль ведётся по журналу приложения (`mr_usage`), а Billing сверяется на следующий день.

### 5.3 Контроль затрат и остановка при аномалиях
**Оперативно (журнал приложения):**
```sql
SELECT provider, model, reconciliation, count(*), sum(estimated_cost) est_kop, sum(cost) charged_kop, sum(actual_cost) observed_kop
FROM mr_usage WHERE feed = 'live' GROUP BY 1,2,3 ORDER BY 1,2,3;
```
Плюс панель «Диагностика последнего прогона» (резерв → факт, вызовы без подтверждённой стоимости, аномалии).

**Немедленная остановка, если выполнено любое условие:**
- `anomaly_over_estimate` ≥ 1 (приложение уже само остановит платные вызовы);
- доля `unknown` > 10 % вызовов моделей или > 2 таймаута подряд;
- получено оповещение Billing на 50 % (до ступени 3) или на 80 % (в любой момент);
- ошибка авторизации (401/403);
- в выдаче или логах замечен секрет;
- приложение показывает сумму больше потолка ступени (не должно случиться — это дефект).

**Как остановить:**
1. Остановить процесс (Ctrl-C или kill). Попытка останется в журнале с полным резервом — это честный учёт.
2. Удалить API-ключ в консоли (сервисный аккаунт → API-ключи) — с этого момента ни один вызов не пройдёт.
3. `unset VL_LIVE_EXECUTE`.
4. Записать время, причину и `SELECT` из `mr_usage` в `research/reviews/phase-b-incident.md`.

**Сверка с биллингом (день 2):** Billing → платёжный аккаунт → **Детализация** по сервисам Search API и AI Studio за дни испытания. Сравнить с `sum(cost)` из `mr_usage`.

## 7. Критерии успеха и условия GO / NO-GO

### Гейт A — разрешение на первый платный вызов (все условия обязательны)
- подготовительный PR смержен, CI зелёный, проверки 2.2 пройдены;
- бюджет Billing создан и проверен;
- ключ с двумя областями и сроком ≤ 7 дней;
- `VL_LIVE_EXECUTE` выставляется только в день запуска;
- письменное разрешение основателя с потолком.

### Гейт B — после пробного вызова
| Условие | GO | NO-GO |
|---|---|---|
| Разбор XML поиска | ≥ 1 документ на каждый из 2 запросов, URL и заголовки корректны | 0 документов при непустой выдаче в консоли — исправить парсер (по сохранённому ответу) до продолжения |
| Ответ моделей | валидный JSON по схеме у обеих моделей (при `json_schema` или после переключения на `json_object`) | невалидный ответ у одной из моделей при обоих режимах |

| Расход ступени | ≤ 5 ₽ | — |
